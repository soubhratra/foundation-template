**Create apps/api/Dockerfile:**
```dockerfile
# Multi-stage production Dockerfile for Django API
# Base image: Debian slim for wheel compatibility
# Final size target: ~150MB

# Stage 1: Builder - Install dependencies
FROM python:3.12-slim AS builder

WORKDIR /app

# Install system dependencies for building Python wheels
RUN apt-get update && apt-get install -y --no-install-recommends \
    build-essential \
    libpq-dev \
    && rm -rf /var/lib/apt/lists/*

# Install uv for fast dependency resolution
RUN pip install --no-cache-dir uv

# Copy dependency files
COPY pyproject.toml ./

# Install dependencies to /app/.venv
RUN uv venv /app/.venv && \
    uv pip install --no-cache -r pyproject.toml

# Stage 2: Runtime - Minimal production image
FROM python:3.12-slim

WORKDIR /app

# Install runtime dependencies only (postgres client, not build tools)
RUN apt-get update && apt-get install -y --no-install-recommends \
    libpq5 \
    && rm -rf /var/lib/apt/lists/*

# Copy virtual environment from builder
COPY --from=builder /app/.venv /app/.venv

# Add venv to PATH
ENV PATH="/app/.venv/bin:$PATH"

# Copy application code
COPY . .

# Create non-root user for security
RUN useradd -m -u 1000 appuser && \
    chown -R appuser:appuser /app
USER appuser

# Expose port
EXPOSE 8000

# Health check
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
    CMD python -c "import requests; requests.get('http://localhost:8000/api/v1/health/', timeout=5)"

# Run gunicorn (production WSGI server)
CMD ["gunicorn", \
     "--bind", "0.0.0.0:8000", \
     "--workers", "4", \
     "--worker-class", "sync", \
     "--timeout", "60", \
     "--access-logfile", "-", \
     "--error-logfile", "-", \
     "config.wsgi:application"]
```

**Design decision (Debian slim over Alpine):** Using python:3.12-slim (Debian-based) instead of Alpine. Research shows Alpine has musl libc compatibility issues with Python wheels (psycopg, numpy, etc.). Debian slim balances size (~150MB) and compatibility.

**Design decision (multi-stage build):** Builder stage installs build tools and compiles wheels. Runtime stage copies only the virtual environment, reducing final image size by 50-70%.

**Design decision (gunicorn workers):** Using 4 sync workers as baseline. Research shows sync workers are simplest and sufficient for most workloads. Template users can switch to gevent/uvicorn workers for async if needed.

**Design decision (non-root user):** Running as appuser (uid 1000) follows security best practices. Never run production containers as root.

**Note:** Database migrations should run separately (not in Dockerfile CMD). Production deployments typically run migrations via init container or pre-deploy script.

**Create apps/web/Dockerfile:**
```dockerfile
# Multi-stage production Dockerfile for Next.js web app
# Base image: Alpine for builder, minimal runtime
# Final size target: ~100-150MB

# Stage 1: Dependencies - Install node_modules
FROM node:20-alpine AS deps

WORKDIR /app

# Install pnpm
RUN corepack enable && corepack prepare pnpm@9 --activate

# Copy package files
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml .npmrc ./
COPY apps/web/package.json ./apps/web/
COPY packages/api-client/package.json ./packages/api-client/
COPY packages/business-logic/package.json ./packages/business-logic/
COPY packages/config-eslint/package.json ./packages/config-eslint/
COPY packages/config-ts/package.json ./packages/config-ts/
COPY packages/ui/package.json ./packages/ui/
COPY packages/validation/package.json ./packages/validation/

# Install dependencies
RUN pnpm install --frozen-lockfile --prod

# Stage 2: Builder - Build application
FROM node:20-alpine AS builder

WORKDIR /app

# Install pnpm
RUN corepack enable && corepack prepare pnpm@9 --activate

# Copy dependencies from deps stage
COPY --from=deps /app/node_modules ./node_modules
COPY --from=deps /app/apps/web/node_modules ./apps/web/node_modules

# Copy workspace files
COPY . .

# Build Next.js app (standalone output enabled in next.config.ts)
RUN pnpm turbo build --filter=@repo/web

# Stage 3: Runner - Minimal runtime image
FROM node:20-alpine AS runner

WORKDIR /app

# Create non-root user
RUN addgroup --system --gid 1001 nodejs && \
    adduser --system --uid 1001 nextjs

# Copy standalone output
COPY --from=builder /app/apps/web/.next/standalone ./
COPY --from=builder /app/apps/web/.next/static ./apps/web/.next/static
COPY --from=builder /app/apps/web/public ./apps/web/public

# Set ownership
RUN chown -R nextjs:nodejs /app

USER nextjs

EXPOSE 3000

ENV PORT=3000
ENV HOSTNAME="0.0.0.0"

# Health check
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
    CMD node -e "require('http').get('http://localhost:3000/api/health', (r) => {process.exit(r.statusCode === 200 ? 0 : 1)})"

# Start Next.js server
CMD ["node", "apps/web/server.js"]
```

**Design decision (standalone output):** Next.js standalone output bundles all dependencies into .next/standalone, enabling minimal Docker images. Research shows this reduces image size by 60-80% compared to copying full node_modules.

**Design decision (Alpine for Next.js):** Using Alpine for Next.js is safe (no native dependencies like Django). Alpine reduces image size to ~100MB vs ~400MB with Debian.

**Design decision (three-stage build):** Separate deps, builder, and runner stages maximize layer caching. Dependencies change less frequently than code, so deps layer is cached effectively.

**Note:** Health check assumes Next.js app has /api/health route. Template users can adjust or remove if not applicable.

**Create docker-compose.prod.yml:**
```yaml
# Production Docker Compose configuration
# Demonstrates production deployment with all services
#
# Usage:
#   docker compose -f docker-compose.prod.yml up --build
#
# Environment variables:
#   - Set DATABASE_URL, SECRET_KEY, etc. in production
#   - Never commit .env files with production secrets

version: '3.9'

services:
  postgres:
    image: pgvector/pgvector:pg16
    environment:
      POSTGRES_DB: ${POSTGRES_DB:-foundation}
      POSTGRES_USER: ${POSTGRES_USER:-postgres}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-postgres}
    volumes:
      - postgres_data:/var/lib/postgresql/data
    ports:
      - "5432:5432"
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 10s
      timeout: 5s
      retries: 5
    restart: unless-stopped

  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 5s
      retries: 5
    restart: unless-stopped

  api:
    build:
      context: ./apps/api
      dockerfile: Dockerfile
    environment:
      DATABASE_URL: postgresql://${POSTGRES_USER:-postgres}:${POSTGRES_PASSWORD:-postgres}@postgres:5432/${POSTGRES_DB:-foundation}
      SECRET_KEY: ${SECRET_KEY:?SECRET_KEY must be set}
      DEBUG: ${DEBUG:-False}
      ALLOWED_HOSTS: ${ALLOWED_HOSTS:-localhost,127.0.0.1}
      REDIS_URL: redis://redis:6379/0
      CELERY_BROKER_URL: redis://redis:6379/0
    ports:
      - "8000:8000"
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
    restart: unless-stopped

  web:
    build:
      context: .
      dockerfile: apps/web/Dockerfile
    environment:
      NEXT_PUBLIC_API_URL: ${NEXT_PUBLIC_API_URL:-http://localhost:8000}
    ports:
      - "3000:3000"
    depends_on:
      - api
    restart: unless-stopped

  celery:
    build:
      context: ./apps/api
      dockerfile: Dockerfile
    command: celery -A config worker -l info
    environment:
      DATABASE_URL: postgresql://${POSTGRES_USER:-postgres}:${POSTGRES_PASSWORD:-postgres}@postgres:5432/${POSTGRES_DB:-foundation}
      SECRET_KEY: ${SECRET_KEY:?SECRET_KEY must be set}
      DEBUG: ${DEBUG:-False}
      REDIS_URL: redis://redis:6379/0
      CELERY_BROKER_URL: redis://redis:6379/0
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
    restart: unless-stopped

volumes:
  postgres_data:

networks:
  default:
    name: foundation-prod
```

**Design decision (health checks + depends_on):** Using health checks with condition: service_healthy ensures services start in correct order. API and Celery wait for Postgres and Redis to be ready before starting.

**Design decision (restart policies):** All services use restart: unless-stopped for production resilience. Services automatically restart on failure.

**Design decision (separate Celery service):** Celery worker runs as separate service using same API image but different command. Shares database and Redis with API.

**Design decision (env var validation):** SECRET_KEY uses ${VAR:?message} syntax to fail-fast if not set. Prevents accidentally running production without secrets.

**Note:** Production deployments should:
1. Run migrations before starting API: `docker compose run --rm api python manage.py migrate`
2. Collect static files: `docker compose run --rm api python manage.py collectstatic --noinput`
3. Use environment files (.env.prod) NEVER committed to git
4. Use managed database services (not Docker Postgres) for production scale
