# Requirements: Foundation Template

**Defined:** 2026-02-08
**Core Value:** A new SaaS product goes from zero to running full-stack app (web + mobile + API + auth) in under 5 minutes with one command.

## v1 Requirements

Requirements for initial release. Each maps to roadmap phases.

### Monorepo Foundation

- [ ] **MONO-01**: Turborepo configured with pnpm workspaces for all JS/TS apps and packages
- [ ] **MONO-02**: Django project lives in monorepo at apps/api/, managed by uv (not pnpm workspace)
- [ ] **MONO-03**: Docker Compose runs Postgres 16 with PGVector extension and Redis locally
- [ ] **MONO-04**: Shared TypeScript config package (tsconfig base) consumed by all JS/TS apps
- [ ] **MONO-05**: Shared ESLint config package consumed by all JS/TS apps
- [ ] **MONO-06**: Environment variable management with .env.example files and validation
- [ ] **MONO-07**: `turbo dev` starts all services with hot reload (hybrid: infra in Docker, apps on host)
- [ ] **MONO-08**: Root package.json scripts orchestrate both Python and JS/TS tasks

### API & Backend

- [ ] **API-01**: Django Ninja Extra REST API with auto-generated OpenAPI 3.1 spec
- [ ] **API-02**: Custom AbstractUser model created before first migration
- [ ] **API-03**: Health check endpoint returns service status
- [ ] **API-04**: Django admin enabled and accessible
- [ ] **API-05**: Database migrations configured and running against Postgres
- [ ] **API-06**: Layered architecture: Controllers (Ninja Extra) / Services (business logic) / ORM (data access)
- [ ] **API-07**: OpenAPI JSON exported to file for type generation pipeline consumption
- [ ] **API-08**: CORS configured for local development (Next.js and Expo origins)
- [ ] **API-09**: Django settings split: base, development, production

### Authentication

- [ ] **AUTH-01**: User can sign up with email and password
- [ ] **AUTH-02**: User receives email verification after signup
- [ ] **AUTH-03**: User can log in with email and password
- [ ] **AUTH-04**: User can log out from any authenticated page/screen
- [ ] **AUTH-05**: User can reset password via email link
- [ ] **AUTH-06**: User session persists across browser refresh (web — session cookies)
- [ ] **AUTH-07**: User session persists across app restart (mobile — JWT in secure storage)
- [ ] **AUTH-08**: Django Allauth configured in headless mode for SPA/mobile clients
- [ ] **AUTH-09**: Dual auth strategy: session cookies for web, JWT tokens for mobile

### Shared Packages

- [ ] **PKG-01**: packages/api-client with auto-generated TypeScript types from OpenAPI spec
- [ ] **PKG-02**: packages/api-client with openapi-fetch typed client wrapper
- [ ] **PKG-03**: packages/validation with shared Zod schemas for forms (signup, login, profile)
- [ ] **PKG-04**: packages/ui with React Native Web primitives (Button, Text, Input, Card)
- [ ] **PKG-05**: packages/business-logic with shared auth hooks (useAuth, useUser)
- [ ] **PKG-06**: packages/business-logic with shared utilities and constants
- [ ] **PKG-07**: Type generation pipeline: Django Ninja OpenAPI spec → openapi-typescript → TypeScript types
- [ ] **PKG-08**: All shared packages consumed by both web and mobile apps

### Web Application

- [ ] **WEB-01**: Next.js 15 App Router with Shadcn/ui component library and Tailwind CSS
- [ ] **WEB-02**: Auth pages: login, signup, password reset, email verification
- [ ] **WEB-03**: Authenticated layout with navigation sidebar/header
- [ ] **WEB-04**: Unauthenticated layout for auth pages
- [ ] **WEB-05**: Dashboard shell page (placeholder content for template users to customize)
- [ ] **WEB-06**: User profile/account settings page
- [ ] **WEB-07**: Dark mode toggle with system preference detection
- [ ] **WEB-08**: Next.js middleware for auth guards (redirect unauthenticated users)
- [ ] **WEB-09**: Server Components with typed API calls via shared api-client

### Mobile Application

- [ ] **MOB-01**: Expo managed workflow app with Expo Router navigation
- [ ] **MOB-02**: Auth screens: login, signup (matching web auth flow)
- [ ] **MOB-03**: Tab-based navigation for authenticated users
- [ ] **MOB-04**: JWT token management with expo-secure-store
- [ ] **MOB-05**: Shared API client consumption (same packages/api-client as web)
- [ ] **MOB-06**: Shared validation schemas consumption (same packages/validation as web)
- [ ] **MOB-07**: Shared UI primitives consumption (packages/ui React Native Web components)
- [ ] **MOB-08**: Profile/account settings screen

### AI Module (Optional)

- [ ] **AI-01**: PGVector extension enabled with model mixin for embedding fields
- [ ] **AI-02**: HNSW index migration for vector similarity search
- [ ] **AI-03**: LangGraph agent scaffold with at least one example graph
- [ ] **AI-04**: Embedding pipeline via Celery background task
- [ ] **AI-05**: Vector search API endpoint (search by similarity)
- [ ] **AI-06**: AI module fully isolated in apps/api/apps/ai/ for clean removal
- [ ] **AI-07**: CLI scaffolder can exclude AI module when generating new project

### DevEx & CI/CD

- [ ] **DX-01**: Pre-commit hooks: ruff (Python), eslint + prettier (JS/TS)
- [ ] **DX-02**: GitHub Actions workflow with 3 parallel jobs: api, web, mobile
- [ ] **DX-03**: CI gate: fail build if generated TypeScript types are stale vs OpenAPI spec
- [ ] **DX-04**: pytest test suite for backend with example tests
- [ ] **DX-05**: vitest test suite for frontend with example tests
- [ ] **DX-06**: detox test suite for mobile with example tests
- [ ] **DX-07**: Production Dockerfiles for Django API and Next.js app
- [ ] **DX-08**: Type checking enforced: mypy (Python), tsc --noEmit (TypeScript)

### CLI Scaffolder

- [ ] **CLI-01**: Interactive CLI asks project name and optional features (include AI module?)
- [ ] **CLI-02**: Generates new project directory with all configs renamed and updated
- [ ] **CLI-03**: Generates unique Django SECRET_KEY and other secrets
- [ ] **CLI-04**: Updates package names across all package.json, pyproject.toml, and config files
- [ ] **CLI-05**: Generated project passes all linting and type checks out of the box

## Out of Scope

Explicitly excluded. Documented to prevent scope creep.

| Feature                     | Reason                                                          |
| --------------------------- | --------------------------------------------------------------- |
| Built-in billing/Stripe     | Too product-specific; each SaaS has different pricing models    |
| Multi-tenancy               | Tenancy model depends on product; template shouldn't constrain  |
| Landing page/marketing site | Every product rewrites this; pure bloat in a template           |
| Blog/CMS                    | Adds complexity for a feature most SaaS products don't need     |
| Social OAuth pre-configured | Requires per-product API keys and setup anyway                  |
| Email service integration   | Provider choice (SendGrid, Resend, SES) is product-specific     |
| Analytics integration       | Provider and event schema are product-specific                  |
| i18n/localization           | Most products start in one language; retrofitting is easier     |
| RBAC/permissions system     | Deeply product-specific; impossible to generalize well          |
| Real-time/WebSockets        | Operational complexity; most SaaS doesn't need it at launch     |
| Error tracking (Sentry)     | Product-specific configuration; easy to add per-project         |
| Admin dashboard (custom)    | Django admin is sufficient for template; product builds its own |
