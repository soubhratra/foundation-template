## Cross-Tool Coordination

OpenSpec does not operate in isolation. This project uses both OpenSpec (specification
management) and GSD (execution engine). Claude Code is the bridge between them.
These rules ensure specs are informed by research and code reality.

### Before Generating or Modifying Any Spec

Read these GSD documents if they exist. They contain human-reviewed decisions
that specs must be consistent with:

**Foundation research (permanent decisions):**
- `.planning/foundation/STACK.md` — Approved tech stack with versions and rationale
- `.planning/foundation/ARCHITECTURE.md` — Approved architecture patterns
- `.planning/foundation/CONVENTIONS.md` — Coding standards per language
- `.planning/foundation/TESTING.md` — Test strategy per layer

**Active research (latest findings):**
- `.planning/research/*` — All files in this directory, if it exists

**Codebase analysis (brownfield projects):**
- `.planning/codebase/STACK.md` — Current tech inventory
- `.planning/codebase/ARCHITECTURE.md` — Current patterns and data flow
- `.planning/codebase/STRUCTURE.md` — Directory layout and key files
- `.planning/codebase/CONVENTIONS.md` — Current coding standards
- `.planning/codebase/TESTING.md` — Current test setup
- `.planning/codebase/INTEGRATIONS.md` — External services and APIs
- `.planning/codebase/CONCERNS.md` — Tech debt and known issues

If any GSD document contradicts a spec you are generating, **flag the conflict**
to the user rather than silently overriding either source.

### Before Creating a Change Proposal (/opsx:new)

1. Read ALL existing specs in `openspec/specs/` to understand the current system.
2. Read `.planning/codebase/*` (if exists) to understand implementation reality.
3. Read `.planning/PROJECT.md` and `.planning/REQUIREMENTS.md` for project context.
4. In the proposal, explicitly reference which apps are impacted:
   - `apps/api/` — Backend changes
   - `apps/web/` — Web frontend changes
   - `apps/mobile/` — Mobile app changes
   - `apps/landing/` — Landing site changes
   - `packages/shared-types/` — Shared type changes
   - `packages/ui/` — Shared component changes

### Baseline vs Change Flow

Use the **correct pattern** based on the situation:

| Situation | Pattern |
|-----------|---------|
| No specs exist yet (fresh project or template) | Write DIRECTLY into `openspec/specs/` |
| Capturing an existing codebase for the first time | Write DIRECTLY into `openspec/specs/` |
| Adding a feature to an already-specced system | Change proposal: `/opsx:new` → review → archive |
| Modifying existing behavior | Change proposal with MODIFIED delta |
| Removing a feature | Change proposal with REMOVED delta |

Do NOT use the change proposal flow for establishing baselines — it creates
implementation tasks that have no corresponding code to write.

## Monorepo Awareness

This project is a monorepo containing multiple apps and shared packages.
Specs must be organized by **domain**, not by app.

### Spec Directory Structure

```
openspec/specs/
├── foundation/          # Tech stack, architecture, conventions (rarely changes)
├── product/             # Product-specific domain specs
├── api/                 # API endpoint and agent specs
├── web/                 # Web page and component specs
├── mobile/              # Mobile screen specs
├── frontend/            # Shared frontend conventions
├── backend/             # Backend conventions (API, ORM, AI patterns)
└── cross-app/           # Specs spanning multiple apps (auth, types, real-time)
```

### Cross-App Specs

When a requirement spans multiple apps, the spec MUST list which app
implements which part. Use this pattern in GIVEN/WHEN/THEN scenarios:

```markdown
### Scenario: [Description]
- GIVEN [precondition]
- WHEN [trigger]
- THEN apps/api/ [backend action]
- AND apps/web/ [web frontend action]
- AND apps/mobile/ [mobile action]
- AND packages/shared-types/ [type update if needed]
```

This makes cross-app dependencies explicit before code is written.

### App-Specific Context

Each app has its own `CLAUDE.md` with pointers to relevant specs:
- `apps/web/CLAUDE.md` — Points to `openspec/specs/web/` and `openspec/specs/frontend/web.md`
- `apps/api/CLAUDE.md` — Points to `openspec/specs/api/` and `openspec/specs/backend/`
- `apps/mobile/CLAUDE.md` — Points to `openspec/specs/mobile/` and `openspec/specs/frontend/mobile.md`

When generating specs for a specific app, read that app's `CLAUDE.md` for
additional context about conventions and patterns specific to that app.

## Stack Constraints

The following tech decisions are FINAL and must not be contradicted in any spec:

- **Backend:** Django Ninja Extra (Python 3.12+), PostgreSQL 16+, PGVector
- **Frontend Web:** Next.js 15+ (App Router), Shadcn/ui, Tailwind CSS 4+
- **Frontend Mobile:** React Native, Expo (managed workflow)
- **AI/Agents:** LangGraph, PGVector for embeddings
- **Monorepo:** Turborepo, pnpm workspaces

If a spec requires technology outside this list, it must explicitly justify
the addition and flag it for human review.

## Quality Rules for Generated Specs

1. **Be specific.** "The system shall handle errors" is useless.
   "The API shall return a 422 response with a `{field, message}` error
   body when validation fails" is actionable.

2. **Include file paths.** Reference actual paths in the monorepo:
   `apps/api/accounts/api.py`, not "the accounts API."

3. **Use GIVEN/WHEN/THEN** for scenarios that agents will implement.
   These become the basis for verification.

4. **Mark cross-app impacts.** Every spec that touches more than one app
   directory must list all impacted apps explicitly.

5. **Don't duplicate foundation specs.** Product specs should reference
   foundation specs, not repeat them. Example: "Authentication follows
   the patterns defined in `openspec/specs/foundation/auth.md`."
